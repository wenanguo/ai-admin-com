## 2026-11-13 · 建立 PM 调度机制

**背景**：原流程（`docs/process.md`）是「人提 issue → 开发 agent 领 → PR → 人合并」。
「人提 issue」全靠手写 ⇒ 验收标准时有时无、里程碑不明确、依赖关系没写 ⇒
开发 agent 领活时不知道优先级，甚至抢跑。GitHub 已有 milestone/issue/label/PR 这些容器，
**缺的只是填料的人** ⇒ 引入 PM 调度层。

### 决定 1：milestone = 版本 · 能力块

- **定了什么**：一条 milestone 命名为 `v0.9 · M1 AIPM 命令层`；版本只做标题前缀，不建空壳版本 milestone。
- **为什么**：选了「按主题分块 + 按版本」两套思路的合并（GitHub milestone 是平的、不能嵌套，合并是唯一解）。
  主题对齐代码模块与 `docs/aipm/docs/04-command-catalog.md` 的能力域；版本提供节奏感。
- **错了的代价**：块切错 ⇒ issue 挂错 milestone，重排成本 = 逐条改 issue 的 milestone（低）。

### 决定 2：领取靠 `ready` 标签 + 依赖标注，块内串行块间并行

- **定了什么**：每个 milestone 的**第一条** issue 才有 `ready`；issue 正文写明「依赖 #xx 合并后才能动」。
- **为什么**：纯串行会让整条流水线变慢（这个仓的 PR 合并节奏本就不快）；纯自由挑会让 agent 抢跑
  （AIPM 内部依赖明确：命令层 → 风险与预测）。折中后：块内按依赖排队，块与块同时开工。
- **错了的代价**：依赖标注漏写 ⇒ agent 抢跑，返工成本中等（一轮 PR 冲突 + 可能的错实现）。

### 决定 3：事实源放仓库，不放 GitHub 界面

- **定了什么**：`docs/pm/roadmap.md`（活的规划）+ `docs/pm/log.md`（本文件）+ `docs/pm/README.md`（角色说明）；
  GitHub 承载执行侧真相。
- **为什么**：聊天会丢上下文；GitHub 界面不承载「为什么这么排」。与 `docs/notes/` 同一逻辑：
  **交接文档让下一棒接得上**。
- **错了的代价**：两侧不同步 ⇒ 规划失真，需要人工对账（成本随 issue 数量上升）。

### 决定 4：高风险四类改动由 PM 抽查 PR

- **定了什么**：AI 闸门 / 权限 / 数据模型 / 动 AiAdmin（FastAPI）那个仓 —— 这四类 PR 我要亲自看；
  其余 CI 绿 + 合并即完成。
- **为什么**：这四类出错的症状是「看起来正常但数据被静默改了」或「越权」，CI 与单测都抓不到；
  而这个仓 PR 量小（当时总共 8 个），抽查成本可忽略。
- **错了的代价**：漏看 ⇒ 静默改数据或越权，代价高（可能需要数据修复）。

### 决定 5：用 `gh` CLI 手工建 issue，暂不写同步脚本

- **定了什么**：`gh issue create` / `gh api` 直接建；不写 `scripts/pm/sync.mjs`。
- **为什么**：当前 issue 量极小（2 条），手工成本低于维护脚本；脚本是工程活，会持续产生维护与测试负担。
- **错了的代价**：issue 上到二三十个后手工变啰嗦 ⇒ 届时补脚本（已有 plan 可参考）。

### 决定 6（顺手）：git remote 切到 SSH

- **定了什么**：本机 `origin` 改为 `git@github.com:wenanguo/ai-admin-com.git`。
- **为什么**：本机 DNS 把 `github.com` 解析到 `20.6.7.17`（连不上，真实地址是 `140.82.x.x`）；
  HTTPS 的 git 端点（`/info/refs`）被重置，而 SSH（22 与 443）通 ⇒ 用 SSH。
  `http.curloptResolve` 已配在仓库级，但 HTTPS 仍不通，**不要切回 HTTPS**。
- **错了的代价**：若换网络环境，SSH 也可能不通 ⇒ 换回 HTTPS 并重配解析。
