### 五条硬约束（写进每条 issue 的验收标准）

1. 容器**必须监听 `0.0.0.0`** —— 否则 nginx 连不上 502，而容器 healthcheck 走 localhost **仍显示 healthy**（AiAdmin 真踩过）
2. AI 的 **SSE 必须关 `proxy_buffering`** —— 否则对话「憋很久才一次性蹦出来」
3. AI 服务的技能路径是 **cwd 相对** ⇒ 镜像 `WORKDIR` 要对
4. `.ai/auth.json` 是凭据 ⇒ **不进镜像层**
5. `/ai-api/` 前缀不能省 —— AI 服务路径也是 `/api/agent/...`，会被 `/api/` 前缀匹配抢走

### 草稿 3 · docker-compose 编排（前端 + AI 服务 + nginx 三条路由）

```markdown
## 目标

写 **docker-compose 编排**，把「前端静态 + AI 服务」跑成一个整体，并让 nginx 把三条流量分对地方：页面 → 前端、业务 API → AiAdmin 后端、AI API → AI 服务。

## 验收标准

- [ ] \`docker compose -f docker/docker-compose.yaml up -d\` 一次起来**前端 + AI 服务**两个容器，且都有 healthy 状态
- [ ] **浏览器打根路径** → 返回前端页面（不是 nginx 默认页）
- [ ] **业务 API 通**：\`/api/...\` → 打到 AiAdmin 后端，请求头与路径**不被改写**（AiAdmin 的 root_path 是 \`/api/v1\`，nginx **不做 rewrite**）
- [ ] **AI API 通**：\`/ai-api/api/agent/...\` → 打到 AI 服务，且**前缀 \`/ai-api\` 被去掉**
- [ ] **SSE 不缓冲**：AI 的事件流经 nginx 后能**逐条**到达浏览器（\`proxy_buffering off\` + \`proxy_read_timeout\` 足够长）
- [ ] **AI 服务只在本机可达**：端口只绑 \`127.0.0.1\`（或只在 docker 内网暴露），公网唯一入口是 nginx 的 80/443
- [ ] \`docker/.env.example\` 列出全部环境变量（端口、AIADMIN_BASE_URL、AIADMIN_MCP_URL、DATABASE_URL、模型 key 占位），**不含真值**
- [ ] 每个服务都有：日志轮转、内存/CPU 限制、\`restart: unless-stopped\`
- [ ] \`docker compose config\` 校验通过；README 里写明启动命令与所需环境变量

## 范围

- 要做：
  - \`docker/docker-compose.yaml\`（服务：\`web\`、\`ai\`；网络、卷、日志、资源限制、healthcheck）
  - \`docker/.env.example\`（**只放占位与说明**；真值走 \`docker/.env\`，且 \`.env\` 进 \`.gitignore\`）
  - nginx 站点配置的**代理部分**：\`location /api/\`（不 rewrite）、\`location /ai-api/\`（去前缀）、\`location /\`（静态 + SPA fallback）
  - 决定并写明：AiAdmin 后端是同 compose 内还是外部地址（外部更简单：用 \`AIADMIN_BASE_URL\` 指向它）
- 不做：
  - 不做镜像构建 —— 草稿 1、2
  - 不做一键部署脚本 —— 草稿 4
  - 不做 TLS 证书与 443（预留挂载点）
  - **不改 AiAdmin 那个仓的 compose**（它自己有一套）
  - 不做数据库/Redis 编排（外部实例，参照 AiAdmin：mysql/redis 在那边是注释掉的）

## 上下文

- **AiAdmin 的对应文件（主要参考）**：\`D:/project/AiAdmin/docker/docker-compose.yaml\`、\`docker/nginx/nginx.conf\`、\`docker/backend/Dockerfile\`、\`docker/.env\`
- ⚠️ **AiAdmin 踩过的坑（别再踩）**：
  1. 容器**必须监听 \`0.0.0.0\`**，否则 nginx 连不上 → 502，而容器 healthcheck 走 localhost **仍显示 healthy**
  2. \`ENVIRONMENT\` 必须**显式钉死 \`prod\`**，否则可能读到 \`.env.dev\`（验证码被关掉）
  3. 后端端口只绑宿主机回环 ⇒ 公网只能走 nginx
- **前端的代理口径**：\`frontend/config/proxy.ts\` ——
  - \`/api/\` → AiAdmin（**不 rewrite**）
  - \`/ai-api/\` → AI 服务（\`pathRewrite: { '^/ai-api': '' }\`）⇒ 生产 nginx 必须一致
  - ⚠️ **必须用独立前缀 \`/ai-api/\`**：AI 服务路径也是 \`/api/agent/...\`，不加独立前缀会被 \`/api/\` 抢走
- AI 服务挂载点：\`/api/agent\`、\`/api/pending\`、\`/api/audit\`（\`backend/ai/src/server.ts\`）
- AI 服务环境变量：\`backend/ai/.env.example\`
- 前端注入的 \`AI_API_BASE_URL\`：\`frontend/config/config.ts\` 的 \`define\`（生产要指到 \`/ai-api\`）
```

### 草稿 4 · 部署脚本 deploy.sh

```markdown
## 目标

写一条**部署脚本** \`docker/deploy.sh\`，把「拉代码 → 构建镜像 → 起服务 → 验证健康 → 失败可回退」变成一条命令（参考 AiAdmin 的 \`deploy.sh\`）。

## 验收标准

- [ ] \`bash docker/deploy.sh\` 一次完成：拉最新代码 → 构建（或复用）镜像 → \`docker compose up -d\` → **等待两个容器 healthy**
- [ ] 脚本**可重复执行**（幂等）：再跑一次不会报错、不重建无变化的东西
- [ ] 有 \`--check\`（只检查，不改动任何东西）与 \`--yes\`（真执行）两种模式，默认**只检查**
- [ ] 依赖检查：开始前检查 \`docker\` / \`docker compose\` 是否可用、Node 版本是否满足（≥ 22），缺什么就明确报缺什么
- [ ] **失败可回退**：构建或启动失败时打印**怎么回退**（如 \`git reset --hard <上一个 commit>\` + \`docker compose up -d\`）
- [ ] 每次部署打印一行摘要：commit、镜像 tag、容器状态、访问地址
- [ ] Windows 上有对应的 \`deploy.bat\`（或明确说明「Windows 走 Docker Desktop + 手敲 compose 命令」）
- [ ] 脚本用 \`set -euo pipefail\`，且**不把凭据写进日志**

## 范围

- 要做：
  - \`docker/deploy.sh\`（主逻辑）+ 可选 \`docker/deploy.bat\`
  - 「上次成功部署的 commit」记录（用于回退提示；放 \`docker/.last-deploy\`，**加进 \`.gitignore\`**）
- 不做：
  - 不做 CI/CD 自动触发（另开 issue；本条是**手工一条命令**）
  - 不做数据库备份与迁移
  - 不做 TLS 证书签发与续期
  - 不改 compose 本身 —— 草稿 3

## 上下文

- **主要参考**：\`D:/project/AiAdmin/deploy.sh\`（git pull → 记录/对比 commit → 自身更新时自动重载 → 可选构建前端 → \`docker compose up -d\`；带彩色日志与 \`check_deps\`/\`load_env\`/\`pull_code\`/\`build_frontend\`）
- ⚠️ AiAdmin 的坑：它的 \`deploy.sh\` 依赖 **pnpm** 且前端在 \`frontend/web\`（Vue），**我们不是**：本仓前端是 \`frontend/\`（Umi 4，npm）⇒ 别照抄它的前端构建逻辑，我们走**镜像构建**
```
