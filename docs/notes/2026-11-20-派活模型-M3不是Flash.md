# 派活的模型：**别用 M3.1-Flash**（实测它只读不写）

## 结论

**派活（PM → 开发 agent）的缺省模型必须是 `MiniMax-M3`（全量），不是 `MiniMax-M3.1-Flash`。**

## 实测（2026-11-20 · #124 连派三轮）

| 轮次 | 模型 | 任务形态 | 结果 |
| ---- | ---- | -------- | ---- |
| 1 | M3.1-Flash | 「造整个管理面」（旧口径） | 67 步 · **零写入** · 被 8192 输出上限截断 |
| 2 | M3.1-Flash | 「先落骨架」+ 任务书进仓 | 45 步 · 100+ 次调用 · **零写入** · 整轮作废 |
| 3 | M3.1-Flash | **只做一个文件** + 禁读源码 | 39 次调用 · **零写入** · 仍去读 httpxy 源码 |
| 4 | **MiniMax-M3** | 同上（只做一个文件） | 7 分钟开始写 · 40 分钟交 **3 个提交 + PR #147** |

⇒ **问题不在任务描述**：任务书、提示词纪律（「先落骨架」「别通读仓库」）都加了，Flash 仍然只读。
⇒ **是模型的行为差异**：Flash 在大仓里无限探索；全量 M3 会动手。

## 配套的三条纪律（已进 `.pi/prompts/dev.md` 与派活消息）

1. **先落骨架并提交**（哪怕是空壳）⇒ 先有 PR，再迭代细节。
2. **别把仓库翻个遍** ⇒ issue / 任务书已指了路径，读完就动手。
3. **别读 dsh / httpxy 的源码** ⇒ 配方写在任务书里，照抄选项名。

## 顺带发现

- **换模型不用改代码**：`DISPATCH_MODEL` 环境变量即可（`backend/ai/.env` 或命令行）。
- 若以后配了 **DeepSeek 官方 key**，派活会自动切到 `deepseek-direct`（`backend/ai/.env` 里写 `DEEPSEEK_API_KEY=` 即可）⇒ dsh 是 DeepSeek 自己的 harness，它自己的模型大概率更贴。
