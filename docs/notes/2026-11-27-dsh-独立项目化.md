## 决策记录（★ 最值钱的部分）

| 决定 | 为什么 | 错了的代价 |
| ---- | ------ | ---------- |
| **目录放仓根 `dsh/`**（不是 `backend/ai/dsh-standalone`） | issue 明写「独立 `dsh/` 项目目录（仓库内，但独立）」⇒ 放仓根 ⇒ 一眼看出它是**另一个项目** | 塞进 `backend/ai/` ⇒ 看不出它独立 ⇒ 以后有人把它的依赖合进服务 |
| **插件按 `file:` 引用装**（不复制源码） | issue 明写「不是复制粘贴源码」⇒ `pnpm add "@ai-admin/dsh-plugin@file:<目录>"` ⇒ **只有一份源码**（`backend/ai/dsh-plugin`） | 复制源码 ⇒ 两份要同步 ⇒ 改一边忘了另一边 ⇒ 「改了插件没生效」 |
| **用户可配变量叫 `STANDALONE_*`**（**不是** `DSH_*`） | dsh 的 app-boot 拒收 `.env` 里的 `DSH_*`（`BOOTSTRAP_PREFIXES`）⇒ 用 `DSH_` 前缀会让人**照着配就炸** | 用 `DSH_*` ⇒ 新人第一步就失败 ⇒ 文档再详细也没用 |
| **profile 用 `dsh-base` + `dsh-headless` 两个 bundle**（手写清单） | headless = 「答一个任务、打印结果、退出」⇒ **一个命令跑一轮对话** ⇒ 新人不用学 dsh 的会话模型 | 用 `sdk` bundle ⇒ 要写客户端代码 ⇒ 「独立项目」变成「又一个集成」 |
| **模型路由写进 profile 的补丁层**（`llm-pi-ai` 那一段） | provider 归位给 dsh 自带的适配器（issue #168 · D5=B）⇒ **不自研 provider**；补丁里只有 `apiKeyEnv` ⇒ 密钥不落盘 | 自研 provider ⇒ 重复实现 ⇒ dsh 升级时两处要改 |
| **插件插进补丁层**（`cordis.patch.yml`），**不挂成 bundle** | bundle 里的插件在 **root 作用域** ⇒ 看不见 agent 作用域里的服务 ⇒ 工具变「unknown tool」 | 挂 bundle ⇒ 插件装上了但工具不在 ⇒ 症状是「模型不听话」 |
| **技能只认 `STANDALONE_SKILL_DIRS`**（`includeDefaultRoots: false`） | dsh 的默认根会把**仓库自己的开发技能**与**开发者私人技能**混进会话 | 不关 ⇒ 会话里混进无关技能 ⇒ 行为不可预测 |
| **判重按「内容指纹」**（sha256），**不按路径** | `pnpm add file:` 是**拷贝** ⇒ 路径永远不变 ⇒ 改了插件等于没改（issue #158 踩过） | 按路径判 ⇒ 改了插件不重装 ⇒ provider / 工具全是旧版 |
| **镜像在构建阶段预热 profile** | 运行时**不需要联网**（插件的依赖在构建期就装好）⇒ 容器起得快、断网也能跑 | 运行时才装 ⇒ 每次起容器都要联网 ⇒ 慢且脆 |
| **静态验收 + 运行时验收分开两个脚本** | 静态那半**不装依赖、不联网、不需要凭据** ⇒ 任何 runner 都能当门禁；运行时那半才需要 pnpm + 联网 | 合成一个 ⇒ CI 里一半时间在等依赖 ⇒ 门禁变慢 |
| **`MiniMax-M3` 做缺省模型**（**不是** M3.1-Flash） | 实测 M3.1-Flash 在 dsh 的 headless 里**只读不写**（本仓派活踩过：三轮 40～60 分钟、100+ 次工具调用、零产出） | 用 Flash ⇒ 新人以为「模型不听话」⇒ 实际是模型不写文件 |
| **npm 装项目依赖，pnpm 只用于 profile** | 仓里的规矩是 `package-lock.json`；而 dsh 的 profile **本来就是** pnpm 工程 ⇒ 尊重两边的机制 | 混用 ⇒ 「本地能装、CI 装不上」 |

## 怎么验

```bash
# ① 静态验收（不装依赖 / 不联网 / 不需要凭据）—— CI 里跑的就是它
node scripts/e2e/dsh-standalone.static.cjs

# ② 运行时验收（**真起 dsh** ⇒ 要装依赖 + pnpm + 联网；**不需要模型凭据**）
cd dsh && npm ci
cd .. && node scripts/e2e/dsh-standalone.cjs

# ③ 手工：照着文档走一遍（= issue 的「找一个人照着做一遍」）
cd dsh
npm ci
cp .env.example .env        # 填 MINIMAX_CN_API_KEY
npm run doctor              # 自检
npm run bootstrap           # 建 profile + 装外部插件
npm run chat -- "用一句话回答：1+1 等于几？"

# ④ 现有服务没被动过
git diff --stat main -- backend/ai frontend | tail -3   # ⇒ 空
```

## 坑与提醒

- ⚠️ **`.env` 里不许写 `DSH_*`** ⇒ dsh 拒收（`BOOTSTRAP_PREFIXES`）⇒ **拒绝启动**。
  ⇒ 本项目一律 `STANDALONE_*`。
- ⚠️ **Windows 上 `pnpm` 只能经 shell 起**（Node 的安全限制：不经 shell 直接 spawn `.cmd` 会失败）
  ⇒ `installPlugin` 用 `spawnSync('pnpm add "..."', { shell: true })`。
- ⚠️ **pnpm 11 的供应链策略会拦「刚发布不到一天」的 rc 包** ⇒ profile 目录里写
  `pnpm-workspace.yaml`（`minimumReleaseAge: 0`）⇒ 版本已精确锁死，不是装最新的。
- ⚠️ **profile 里的插件是「拷贝」** ⇒ 改插件要**重跑 `npm run bootstrap`**（内容指纹变了才重装）。
- ⚠️ **npm 11 有 `allow-scripts` 门槛**（koffi / node-pty / protobufjs 的 install 脚本默认不跑）
  ⇒ 本仓 CI 钉 **npm 10.9.9**（没有这门槛）⇒ CI 与本地行为一致。
  ⇒ 本地若用 npm 11 且某个原生包报缺文件 ⇒ `rm -rf node_modules/<包>` 后 `npm install` 重装。
- ⚠️ **`dsh/package-lock.json` 是 npm 11 生成的**（lockfileVersion 3）⇒ npm 10.9.9 也能 `npm ci` ✔。
- ⚠️ **比 lock 有没有被改，要比「基线 → HEAD 的树」**（`git diff <base> HEAD -- <lock>`），
  **不要比工作区**（`git diff <base> -- <lock>`）⇒ 本仓的 lock 在 blob 里是 **CRLF**
  ⇒ Linux runner 上 checkout 后工作区是 LF ⇒ 明明没改却报「改了」⇒ **假红**
  （本条第一版就是这么写的，CI 真的红了 ⇒ 已修，坑记在这儿）。
  ⇒ 基线取 **merge-base**：本地 = 分支点；CI 里 HEAD 是**合并提交** ⇒ merge-base = main 的 tip。
- ⚠️ **git 的 pathspec 相对「cwd」，不是仓根**！⇒ 在 `dsh/` 里跑（CI 的 job 就是）时，
  `-- package-lock.json` 指的是 **`dsh/package-lock.json`**（我新建的那个 ⇒ 假红），
  而 `-- frontend/package-lock.json` **匹配不到**（⇒ 假绿）。
  ⇒ 路径一律写 **`-- :(top)<路径>`**。
  ⇒ ⚠️ **验收脚本要在哪个目录跑都得对** ⇒ 本仓的脚本都从 `__dirname` 推绝对路径。
- ⚠️ **`dsh/.dsh-home/` 是本地的 profile**（含插件拷贝与会话）⇒ 已被 gitignore。
