## 决策记录（★ 最值钱的部分）

| 决定 | 为什么 | 错了的代价 |
| ---- | ------ | ---------- |
| **判据用「内容指纹（sha256）」而不是「依赖路径」** | `pnpm add file:<路径>` 是**拷贝**（不是 link）⇒ 路径永远不变 ⇒ 拷贝永远不刷新。路径判据永远为真 ⇒ 永远跳过 | 插件改了不生效 ⇒ provider / 工具全是旧版 ⇒ 派活瘫（本次的真事） |
| **指纹没变就「不重装」**（不是每次都 `pnpm add`） | pnpm 装东西**要联网、要时间**（本机实测一次 ≈ 1s，生产更慢）⇒ 每次会话都装不可接受 | 派活慢十倍；离线环境直接挂 |
| **指纹变了就重跑 `pnpm add file:…`**（不先删旧拷贝） | 实测（pnpm 11.22）：`pnpm add file:<目录>` 会把目录**重新打包**⇒ 内容变了 integrity 就变 ⇒ 拷进去的是新内容（验收脚本第二段用**真 pnpm** 钉住这条） | 若 pnpm 哪天不重新打包 ⇒ 改了插件仍然不生效（⇒ 这条要有验收脚本盯着） |
| **状态文件放 profile 目录**（`.ai-admin-plugin.json`） | profile 在**卷**上 ⇒ 状态跟着持久化 ⇒ **跨进程 / 跨镜像升级**也判得出「镜像里的插件变没变」（生产那条更严重的问题一并修掉） | 状态丢了 ⇒ 多装一次（无害）；状态与内容对不上 ⇒ 该装时装 |
| **去掉「每个进程只做一次」的长缓存** | 贵的只有「重装」；「检查」（算指纹 + 读状态）是毫秒级 ⇒ 不缓存 ⇒ **同一个进程里改了插件，下一个会话就生效** | 缓存 ⇒ 改了插件要重启服务才生效（回到老毛病） |
| **指纹算法写了两份**（服务侧 TS + 派活侧 CJS），**两边测试钉住同一个 fixture 哈希值** | 服务侧是 ESM TS（在 `backend/ai` 里，**不能** import 仓根 `scripts/`）⇒ 派活侧是 CJS ⇒ 没法共用一份源码 | 两份算法漂了 ⇒ 状态互相不认 ⇒ 反复重装（但**不会算错**，只是慢）⇒ 用 fixture 钉死 |
| **测试用「假 pnpm」**（PATH 前面放一个 `pnpm.cmd`/`pnpm`） | 真 pnpm 要联网、要装依赖 ⇒ CI 跑不动 ⇒ 测的就不是「我们的判据」了 | 测「装得上」⇒ **正好漏掉出问题的那一半**（旧代码就是这么绿的） |
| **不动 dsh 版本（仍锁 `0.2.2-rc.5`）、不动插件功能、不动对外契约** | issue 的「不做」栏是硬边界 | 范围外 ⇒ 需求变更要人拍板 |

## 坑与提醒

- ⚠️ **这个坑的根子是「把路径当成了内容」** ⇒ 凡是把源码装进**别人**的工程
  （`pnpm add file:` / `npm pack` / 复制目录），判据都得是**内容**，不是路径。
- ⚠️ **profile 在卷上 ⇒ 镜像升级后插件不更新**（生产比开发更严重）——
  指纹判据把这条一起修掉了，但**别再写回「路径一样就跳过」**。
- ⚠️ `pnpm add file:` 拷的是**目录** ⇒ 插件目录里**不要**留 `node_modules`
  （会被一起拷进去）；指纹计算**忽略** `node_modules` / `.git` 等目录。
- ⚠️ 测试里的「假 pnpm」要**同时改 profile 的 `package.json`**（真 pnpm 会写依赖）
  ⇒ 否则「依赖还在不在」那条判据永远不成立 ⇒ 每次都重装（测试会红）。
- ⚠️ `scripts/agent/merge-pr.test.cjs` 在 Windows 上有个**先前就存在**的失败
  （`git worktree remove` 撞 8.3 短路径）⇒ 与本单无关，别误伤。
- ⚠️ 指纹**每次会话**都会算一次（插件目录 8 个文件 ⇒ 毫秒级）⇒ 别把插件目录做大
  （要塞大文件 ⇒ 先想想要不要进指纹）。
