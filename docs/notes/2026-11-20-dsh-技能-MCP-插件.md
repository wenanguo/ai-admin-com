## 决策记录（★ 最值钱的部分）

| 决定 | 为什么 | 错了的代价 |
| ---- | ------ | ---------- |
| **技能：自己写 loader**（不继续用 pi 的 `loadSkills`） | `SKILL.md` 是 **Agent Skills 标准格式**（不是 pi 私有）⇒ 自己扫得 ⇒ 技能资产不绑在 pi（#123 的前置） | loader 与 pi 的口径可能漂 ⇒ 有一条**对照测试**盯着（同一批目录 ⇒ 同一批技能） |
| **技能正文一个字不改**（连 frontmatter 都不动） | 技能是提示词 ⇒ 走 git 评审（`AGENTS.md`） | — |
| **模型侧的工具名**仍叫 `mcp__<server>__<tool>`（**只**归一化给人看的地方） | **技能正文里写的就是 `mcp__aiadmin__create_task`** ⇒ 模型侧改名 ⇒ 技能正文与模型看到的东西对不上 | 界面显示的名字与技能正文不一致（人读着别扭，模型不受影响） |
| **只有 dsh 路径归一化工具名**（pi 路径保持原样） | 不改现有产品的显示 ⇒ 最小爆炸半径；#123 拔 pi 时自然统一 | 两个 runner 的界面显示名不同（**已知缺口**，记在 spec §6） |
| **MCP 用 dsh 自带的 `@deepseek-ai/dsh-mcp-client`**（不自己写协议） | MCP 是标准协议；dsh 的客户端已经在尖峰里实测过 ⇒ 少一处升级风险 | 依赖 dsh 的 RC 包（版本锁钉死） |
| **程序化调用它的 `apply(ctx, config)`**（不写 YAML） | 服务器清单**运行时算** ⇒ per-用户 token 天然成立（D6 不再卡在这层） | 用到了它的内部 API（RC ⇒ 可能变 ⇒ 变更只影响 `dsh-plugin/src/mcp.js`） |
| **MCP 的写操作靠 `tools/pre-execute` ⇒ `ask`** | MCP 的工具是 dsh 直接注册的 ⇒ 不走命令桥 ⇒ 闸门看不见它 ⇒ 口径会被绕过 | D4 说 `ask` 在**根作用域**插件里没触发 ⇒ 我们的插件在**补丁层**（agent 作用域）⇒ 实测触发正常 |
| **业务插件零改动**（只改挂法） | 插件提供「能力」，内核 + dsh 侧插件决定「怎么挂」⇒ 换业务系统只改 `src/plugins.ts` | — |
| **`PendingWaiterRegistry` 记住「先到的决定」** | 挂起流程是「先通知外面 ⇒ 再等」⇒ 人立刻点头 ⇒ 决定会**先于**等待者到达 ⇒ 之前被丢掉 ⇒ 批准永远等成超时 | 不修 ⇒ 「批准」在 dsh 路径上等于「拒绝」（**功能坏**） |
| **`decide()` 的返回值语义不变**（没人等 ⇒ 仍返回 false） | 批准 / 拒绝端点的语义（「已处理过 ⇒ 409」）不能变 | — |

## 坑与提醒

- **e2e 的 MCP 服务器走 stdio**（生产走 streamable-http）⇒ 传输层没在 e2e 里覆盖
  （同一个客户端；配置生成有单测）。
- **dsh 侧插件是纯 JS**（跑在 dsh 进程里）⇒ 改完**立即生效**（`pnpm add file:` ⇒ 拷贝进 profile ⇒
  改了要**重跑 profile 引导**才生效；e2e 每次都是新的 `DSH_HOME` ⇒ 不用管）。
- **dsh 的 stderr 被 SDK 客户端吞了**（只在「运行时意外死掉」时才吐尾巴）⇒
  插件里的 `console.error` 在外面**看不见** ⇒ 调试要写文件（`DSH_AI_DEBUG_LOG`）。
- **pnpm 的供应链策略**：`minimumReleaseAge: 0`（profile 引导里已经写了）⇒ 否则 rc 包装不上。
- **peer 依赖要显式装**：`dsh-mcp-client` 的 peer（`dsh-attachment` / `dsh-subprocess` / `dsh-timeout`）
  已经加进 `dsh-plugin/package.json` 与版本锁的 `peerDependenciesInstalledExplicitly`。
- **e2e 需要假环境变量**（内核的 env 校验在模块加载时跑）⇒ 用 `scripts/e2e/fixtures/env.ts`
  （**必须第一个 import**）。
